Before you start

Two shell variables carry through every example on this page. Set them once and every curl below is copy-paste.

BASE=http://localhost:5000/api/v1
TOKEN=<paste the accessToken from the login below>

Getting a token

Login is two steps: the password returns an OTP, the OTP returns the tokens. In development, set DEFAULT_OTP=true in .env and the OTP is always 123456 with no email sent.

POST /auth/login

Step 1 — prove the password

Checks the password and emails a one-time code. It does not return a token; nothing is signed in yet.

curl -s -X POST "$BASE/auth/login" \
  -H "Content-Type: application/json" \
  -d '{ "email": "you@rstartec.com", "password": "..." }'
POST /auth/verify-otp

Step 2 — exchange the code for tokens

Returns accessToken (15 minutes) and refreshToken (7 days). Put the access token in $TOKEN.

curl -s -X POST "$BASE/auth/verify-otp" \
  -H "Content-Type: application/json" \
  -d '{ "email": "you@rstartec.com", "otp": "123456" }'

Every curl on this page sends -H "Authorization: Bearer $TOKEN". A 401 almost always means the 15 minutes ran out — call /auth/refresh or log in again.

Every response has the same shape

Success and failure both come back in one envelope, so a client can parse them the same way. data is null rather than absent when there is nothing to return.

Success
{
  "success": true,
  "statusCode": 200,
  "message": "Leave balance fetched",
  "data": { ... },
  "meta": { "total": 12 }     // only when it paginates
}
Failure
{
  "success": false,
  "statusCode": 409,
  "message": "You already have leave applied for on one or more of those dates",
  "data": null,
  "details": { "code": "LEAVE_REQUEST_OVERLAP", ... }
}

Branch on details.code, never on the message. The code is a stable contract; the message is wording somebody will improve one day. Section 20 lists the codes you will actually hit.

01

The order things have to exist in

Most "why did this 400?" moments are a missing prerequisite rather than a bad request. This is the dependency chain, and it is worth reading once.

Attendance
  1. A locationEmployees point at one. Holidays and shifts hang off it.
  2. A shiftWith week-offs. Until one exists, nothing knows which days are working days — so every day looks absent.
  3. Holidays for the yearPer location. The nightly close marks them; the leave charge skips them.
  4. Then people can punchCheck-in resolves a shift, decides which day the punch belongs to, and writes the day.
Leave
  1. A leave cycleOne FINANCIAL and one CALENDAR covering today. Without one, applying fails with LEAVE_CYCLE_MISSING.
  2. A leave typeMaster data — already seeded.
  3. A policyHow the category behaves: accrual, quota, half days, sandwich rule.
  4. A mappingWho is offered it. No mapping, no category on the apply screen — LEAVE_NOT_MAPPED.
  5. A balanceFrom accrual, or granted by hand. Then people can apply.

npm run db:seed:attendance does the whole right-hand column and the shifts, as a starting point for HR to edit. It deliberately does not create holidays — those differ per country and per year.

Policy and mapping are two different questions, and keeping them apart is the one piece of the leave model worth understanding before you touch the API.
  • Mapping — is this category offered to this person at all? Matched on location, employment type, gender and tenure.
  • Policy — if it is, how does it behave? Accrual, quota, half days, approvals, sandwich rule.
Maternity leave offered to women in India with a year's service is a mapping. That it accrues nothing and needs HR's signature as well as the manager's is a policy. One policy can serve several mapped cohorts, which is why they are not one table.

A day in the life

Three calls cover the whole daily loop. The time always comes from the server — never from the request body — because an attendance record whose time the user chooses records nothing.

POST /attendance/me/check-out

Check out

Appends an OUT punch and re-grades the day: pairs the punches, subtracts the unpaid break, compares against the shift’s full-day and half-day minutes, and sets the status.

curl -s -X POST "$BASE/attendance/me/check-out" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
Response 200
{
  "attendanceStatusId": 2,
  "firstCheckInAt": "2026-11-06T05:22:26.696Z",
  "lastCheckOutAt": "2026-11-06T05:22:27.557Z",
  "workedMinutes": 0,
  "lateMinutes": 0
}

In this capture the two punches are seconds apart, so workedMinutes is 0 after the 60-minute break is deducted — and the day grades as ABSENT. That is the arithmetic working, not a bug.

The two states a client gets wrong

Both are answered before anything is written, so neither can leave a half-finished day behind.

Checking out with nothing open

{
  "success": false,
  "statusCode": 409,
  "message": "This employee already has a shift covering those dates",
  "data": null,
  "details": {
    "code": "SHIFT_ASSIGNMENT_OVERLAP",
    "conflictsWith": {
      "employeeShiftId": 1,
      "shiftId": 3,
      "effectiveFrom": "2036-11-03",
      "effectiveTo": null

Applying for leave, and what it does to the balance

This is the flow worth understanding properly. There is no stored balance anywhere. Every figure is a sum over an append-only ledger, and each step below writes a row to it.

ApplyHOLD +3 IsHold = 1reserved, not yet spent
ApproveREVERSAL −3 IsHold = 1  +  DEBIT −3hold cleared, days charged
RejectREVERSAL −3 IsHold = 1hold cleared, nothing charged
WithdrawREVERSAL +3days given back after approval

A hold is a flag, not a negative number. balanceDays ignores held rows; availableDays is the balance minus them. A negative held value would be subtracted twice the first time anybody summed the column.

When the balance runs out

Leave Without Pay is not a balance to spend — it is a count of days consumed, and it is what every other category falls through to.

The split is applied day by day, earliest first, because payroll deducts for particular dates and not for a total. Somebody with one day left who applies Monday to Wednesday is paid for Monday and unpaid for the other two — which is both what they would expect and what the payslip has to say.

The one explicit prohibition in the HR document: LWP must never be deducted from a paid leave balance. In the ledger that means an LWP_DEBIT row is counted in its own bucket — lwpDaysConsumed — and never reduces balanceDays. A paid balance cannot go negative as a result of unpaid leave.

Comp-off: two separate acts

The HR document is explicit: a comp-off is never credited merely because attendance exists on a weekend. The manager agrees the work happened; HR then grants the day, by hand. Approval alone credits nothing.

ClaimPENDING_MANAGERemployee raises it
ApproveAPPROVED_AWAITING_CREDITno ledger entry — the balance does not move
CreditCREDITED + COMP_OFF_CREDIT +1HR grants the day
